# Plan 009: Pluralise Ingredient Names at Display Time

## Status: Shipped

Tracks [issue #24](https://github.com/gotofritz/nutrisho-django-prototype/issues/24).

## Goal

Nothing in the app pluralises. `recipe_scale` **persists** scaled quantities, so
doubling a recipe writes `quantity=2` and `_ingredient_display.html` renders
**"2 onion"**.

A plural is not a different ingredient — it is the display form of one ingredient
at a quantity other than 1. `1 onion` and `2 onions` are the same `Ingredient`
row. So pluralising belongs in the presentation layer, alongside
`format_quantity`, and never in storage or export.

This is a third variant class, distinct from the two already covered:

| class | example | mechanism |
|---|---|---|
| case | `Onion` / `onion` | `ingredient_name_ci_unique` + `find_ingredient_duplicates` |
| alias | `eggplant` → `aubergine` | resolve on input — [plan 008](008-ingredient-aliases.md) |
| **plural** | `onion` → `onions` | **this plan — display time, from quantity** |

An `onions` row sitting next to `onion` is therefore bad data, not a variant to
alias: it gets merged into the singular with the clean-up tool, and the display
adds the "s". Back-filling existing plural rows is a merge, not a migration — but
the clean-up tool has to *surface* those pairs before anyone can merge them,
which is phase 5.

## Decisions

1. **Plural when `quantity != 1`.** `0.5 onions`, `2 onions`, `1 onion`. Quantity
   `None` (unrecorded) stays singular — there is no count to disagree with.
2. **Only when `unit` is empty.** `2 onions` pluralises; `200 g onion` must not
   become `200 g onions`. The unit check is what keeps mass nouns safe, and it is
   why no dependency is needed for the long tail.
3. **Rule plus a `plural_name` override on `Ingredient`.** English food nouns are
   irregular enough that `+s` breaks immediately (`tomato` → `tomatoes`,
   `chilli` → `chillies`, `leaf` → `leaves`). A rule covers the common endings; the
   field handles the rest. Blank means "derive from the rule". Setting
   `plural_name` equal to `ingredient_name` is how an invariant noun (`broccoli`,
   `fish`) opts out.
4. **The rule lives in `recipes/utils/pluralise.py`**, a pure function with no
   Django imports, next to `filename.py` and `sequencing.py`. The template filter
   is a thin presentation wrapper over it, so the rule is unit-testable without a
   request or a database.
5. **`Ingredient.plural` property** — `plural_name or pluralise(ingredient_name)`.
   One place resolves override-vs-rule, used by the filter and by the clean-up
   tool's pair detection alike.
6. **Export is untouched.** `export_recipes_to_yaml` keeps writing the canonical
   singular — that is data, not presentation. `plural_name` is deliberately *not*
   added to `lossy_fields`: it lives on the shared `Ingredient` table, not on the
   recipe, so it is not recipe data being dropped on round-trip.

### The rule

Applied to the **last whitespace-separated word** only, so `spring onion` →
`spring onions`. Checked in order; first match wins:

| ending | result | example |
|---|---|---|
| already ends `s` | unchanged | `oats`, `chives`, `asparagus` |
| `x`, `z`, `ch`, `sh` | `+es` | `squash` → `squashes` |
| consonant + `y` | `y` → `ies` | `berry` → `berries` |
| consonant + `o` | `+es` | `tomato` → `tomatoes` |
| `i` | `+es` | `chilli` → `chillies` |
| `fe` | `fe` → `ves` | `knife` → `knives` |
| `f` | `f` → `ves` | `leaf` → `leaves` |
| anything else | `+s` | `onion` → `onions` |

"Already ends `s` → unchanged" is the domain-specific one: food nouns ending in
`s` are nearly always already plural or mass (`oats`, `greens`, `capers`,
`noodles`), so `+es` would be wrong far more often than right. `bus`-style nouns
do not occur here, and `plural_name` covers it if one ever does.

Known misses, all handled by the override field: `chief`-type `f` words,
`avocado` → `avocados`, invariant nouns (`fish`, `broccoli`), and head-noun
phrases (`clove of garlic`).

## TDD phases

Each cycle is **red → green → refactor**. Run `task qa` before the PR; keep
coverage ≥ 95%.

- **1** `recipes/utils/pluralise.py`: `pluralise(name: str) -> str` implementing
  the rule table. Pure, no Django.
  - Tests: one case per table row; multi-word pluralises the last word only;
    empty string returns empty; leading/trailing whitespace does not leak into
    the suffix.
- **2** `Ingredient.plural_name` (`CharField(max_length=64, blank=True,
  default="")`) plus migration 0014, and the `Ingredient.plural` property
  resolving override-then-rule.
  - Tests: blank `plural_name` derives from the rule (`tomato` → `tomatoes`);
    a set `plural_name` wins verbatim; `plural_name` equal to the singular makes
    the ingredient invariant; the field is optional (existing rows migrate to
    `""`, no prompt).
- **3** Template filter `display_ingredient_name(iir)` in
  `recipes/templatetags/recipe_filters.py`, taking the `IngredientInRecipe` so it
  can read name, quantity and unit together. Returns `iir.ingredient.plural` when
  `quantity is not None and quantity != 1 and not unit`, else the singular.
  - Tests: `2` + no unit → plural; `1` + no unit → singular; `0.5` + no unit →
    plural; `200` + `g` → singular; `quantity=None` → singular; `Decimal("1.00")`
    → singular (value comparison, not string).
- **4** Apply the filter in `recipes/partials/_ingredient_display.html` and
  `recipes/ingredient_admin/_recipe_preview.html`.
  - Tests: recipe detail page renders `2 onions` and `1 onion` for the same
    ingredient row at different quantities; the clean-up tool's preview pane does
    the same; `200 g onion` is untouched on both. Substitutes
    (`— or <substitute>`) stay singular — out of scope below.
- **5** Clean-up tool catches plural pairs:
  - `find_plural_duplicates() -> list[list[Ingredient]]` in
    `recipes/services/ingredient_admin.py` — pairs a row with the row whose name
    matches its `plural` (case-insensitively), so `onion`/`onions` group
    together, singular first.
  - `search_ingredients(query, *, unused_only=False, plurals_only=False)` — a
    third column-2 filter listing only rows in such a pair, mirroring how
    `unused_only` already narrows the list, wired into the manager's filter row
    next to "unused".
  - `find_ingredient_duplicates` management command also reports plural pairs,
    under their own heading, pointing at the same merge workflow.
  - Tests: `onion` + `onions` group; `tomato` + `tomatoes` group (rule, not
    `+s`); an override-driven pair (`plural_name` set) groups; a lone singular
    does not; `plurals_only` narrows column 2 and composes with `q` and
    `unused_only`; the command lists both classes and exits cleanly with neither.
- **6** `IngredientForm` gains `plural_name`, so the Edit panel can set an
  override. Blank stays valid.
  - Tests: the edit panel renders the field; saving an override persists and
    changes what the recipe page shows; blank clears back to the rule.
- **7** Export regression: `export_recipes_to_yaml` writes `ingredient_name`, never
  the plural, for a scaled recipe.
  - Test: a recipe with `quantity=2`, no unit, exports `name: onion`.
- **8** Docs: `docs/initial-context.md` (template filters, key models, clean-up
  tool's third variant class) and this plan archived per AGENTS.md.

## Out of scope

- Pluralising units themselves (`2 cups`).
- Pluralising the substitute name in the preview (`— or onions`): the quantity
  belongs to the primary ingredient, and a substitute is named, not counted.
- Alias resolution ([plan 008](008-ingredient-aliases.md)).
- A data migration back-filling plural rows — that is a merge, by hand, in the
  clean-up tool.
- Locales other than English.

## Outcome (2026-09-14)

Shipped as planned, with one addition found in review:

- **Phase 9 — a `Merge plural` action.** Phases 5 and 6 left the fix implicit:
  the tool *found* `apple`/`apples`, but the only way to act on it was plain
  Merge, which deletes the plural row without recording its spelling, plus a
  separate Edit to type the plural back in from memory. For pairs the rule
  already derives, the display came out right by luck; for anything it does not
  (`chili`/`chilis` — the rule says `chilies`) the spelling was simply lost.
  So a fourth column-1 action: exactly two selected, the likely singular
  preselected by `suggest_singular`, and `merge_plural_ingredients` writes the
  deleted row's name verbatim onto the survivor's `plural_name` in the same
  transaction as the repoint. Verbatim even when the rule agrees, so the plural
  column always shows where the merged name went.
- **`_guard` gained a maximum.** `_SELECTION_BOUNDS` replaces
  `_MINIMUM_SELECTED`: merging a plural is capped at two, since with two plural
  rows selected there is no way to tell which spelling should win. Every other
  action keeps a minimum only.
