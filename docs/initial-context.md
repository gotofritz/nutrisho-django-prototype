# Initial Context

## Overview

Nutrisho is a Django recipe manager prototype. Stores recipes, ingredients, cuisines, and tags.

## Tech Stack

- **Runtime**: Python 3.14
- **Framework**: Django 6.1 (move to the 6.2 LTS by spring 2027, then stay on LTS releases; see `docs/developer-guide.md`)
- **Frontend**: HTMX 2.x (via django-htmx) — inline partial swaps, no full-page reloads
- **DB**: SQLite, WAL mode with IMMEDIATE transactions
- **Deps**: uv
- **Lint**: ruff
- **Types**: ty
- **Tasks**: GNU Make (targets in `Makefile`, `make help` lists them; ruff config in `.ruff.toml`)
- **Tests**: pytest + pytest-django

## Prerequisites

- `uv` — dependency manager and task runner for Python
- `make` — task runner (`make <target>`, `make help` to list targets)
- `jq` — required by `.claude/hooks/` for JSON parsing (`brew install jq` / `apt install jq`)

## Architecture

Single Django app (`recipes`) under `src/` layout. No API layer. Frontend is server-rendered Django templates with HTMX inline editing. Debug toolbar enabled in dev: it is a `dev` dependency group package, so `urls.py` mounts it only when `debug_toolbar` is in `INSTALLED_APPS` (`settings/dev.py`), and a `uv sync --no-dev` install never imports it.

### Inline Editing Pattern

Each editable entity (field, step, ingredient, group) has three endpoints:
- `GET /<entity>/` — read-only partial (`_*_display.html`)
- `GET /<entity>/edit/` — edit widget partial (`_*_edit.html`)
- `POST /<entity>/save/` — validates and saves; returns display partial on success, edit partial with errors on failure

HTMX swaps partials in place (`hx-swap="outerHTML"`). The `+ Add` buttons (`hx-post`, `hx-swap="beforeend"`) only render a blank edit form — no row is created until its Save posts to the entity's `POST /<entity>/create/` endpoint and validation passes. The draft form submits its DOM `position` (computed at submit via `hx-on::config-request`) and the server inserts at that position (resolved against the ordered sibling list — legacy imported sequences may be 1-based or gapped), shifting later rows, so saving multiple drafts out of order cannot diverge from the on-screen order; Cancel on an unsaved form just removes it from the DOM, so canceled adds leave no orphan rows. `Delete` buttons use `hx-post` with `hx-swap="outerHTML"`. CSRF token is injected globally via `hx-headers` on `<body>`. HTMX library is served from `django_htmx` static files (`htmx.min.js`).

Failed requests are not swapped: the `htmx-config` meta in `base.html` swaps 2xx/3xx and 422 (validation errors re-render the edit form) and marks everything else as an error with `swap: false`, so an open edit form keeps the typed text. One global listener in `base.html` catches `htmx:responseError`, `htmx:sendError` and `htmx:timeout` and shows the fixed `#save-error` banner ("Your change was not saved." for writes, "That did not load." for GETs), with a reload hint on 403/404 (stale CSRF token, row deleted in another tab) and a connection hint on network errors. It is dismissible and hides itself when a later write succeeds. With `DEBUG=True`, django-htmx's debug script replaces the page with Django's error page on a 4xx/5xx before the banner can show, so check the banner with `DEBUG=False`.

Ingredient name edit uses an HTML5 `<datalist>` for autosuggest (all existing ingredient names). On save, `ingredient_name` is resolved via get-or-create so renaming creates a new `Ingredient` rather than mutating a shared one.

### Recipe Duplication (`recipes/services/recipe_duplication.py`)

"Duplicate recipe" copies rows generically: `_clone` reads every
`_meta.concrete_fields` column except the pk and takes overrides by attname
(`recipe_id`, `ingredient_group_id`), so foreign keys are copied by id and a column
added to `Recipe`, `Step`, `IngredientGroup` or `IngredientInRecipe` is carried
over without editing the service (#35). Each level is one `bulk_create` and tags
one `add`, so a copy costs a fixed number of queries whatever the recipe's size.
Only the name allocation retries, inside its own savepoint; an IntegrityError on a
child row rolls the whole copy back. `tests/recipes/test_recipe_duplication.py`
walks every concrete field of the four models and fails if its fixture leaves one
at its default, so a new column must be added to that fixture.

### Scaling (`recipes/utils/scaling.py`, `recipes/services/recipe_scaling.py`)

Scaling is presentation, not a write (#36). `GET /recipes/<id>/?servings=N` shows
the recipe at N servings: the view parses N (`parse_servings`: a whole number from
1 to 32767, anything else is ignored and the stored recipe is shown), turns it into
an exact `Fraction` of the stored servings (`scale_factor`, None when N equals the
stored count) and the template scales each quantity on render with the
`scaled_quantity` filter. A quantity is multiplied before it is divided and every
view starts from the stored value, so nothing drifts (÷3 then ×3 is still `1`).
Display rounding is two decimals half up, but a non-zero amount below 0.01 keeps two
significant digits instead of showing as `0`. The URL is the state, so a scaled
page is bookmarkable and printable.

A scaled page renders `_scaled_ingredients.html`, a read-only list, instead of the
inline editors: those would show and save stored quantities, and the servings
field would be ambiguous. The "Serves N" line is followed by "scaled from M, not
saved · Reset"; Reset links to the unscaled page. Pluralisation follows the
displayed quantity (`ingredient_name_at`), so 1 onion doubled reads "2 onions".

The scale panel asks for a serving count rather than a factor. "Show" is a plain
GET to the recipe page; "Save as scaled copy" POSTs to `scale/copy/`, which calls
`save_scaled_copy`: `duplicate_recipe` (#35), then the copy's servings are set to N
and its quantities, still equal to the original's, are scaled and stored at the
column's two decimals. A quantity that would overflow `DecimalField(7, 2)` or round
a non-zero amount to `0.00` raises `ScaleError` inside the transaction, so nothing
is created and the panel shows the error (422). Nothing writes scaled values onto
an existing recipe.

### Ingredient Clean-up Tool (`recipes/services/`, `recipes/views/ingredient_admin.py`)

A self-contained subsystem under `/recipes/ingredients/manage/`, separate from both
the per-recipe inline editor and Django admin. `Ingredient` rows are shared by every
recipe, so this is where duplicates and spelling variants get edited, deleted or
merged. Staff-only (see **Shared vocabularies** below); the `manage/` URL prefix keeps it clear
of the per-recipe `<recipe_id>/ingredients/...` routes.

The UI is four Miller columns — actions, ingredients, matching recipes, recipe
preview. Clicking an action collapses columns 2-4 into a full-width workspace panel
and turns the clicked button into Cancel. Column 4 is a fresh inert template, not a
trimmed `partials/_recipe_content.html`: that one pulls in the navbars and its field
includes carry `hx-get` edit triggers.

Column 4 follows column 3 rather than holding state of its own: every response
that rebuilds the matches rebuilds the preview with it. Exactly one match previews
itself — there is nothing else to pick — and any other count clears the pane, so a
preview can never outlive the matches it came from.

**Services layer.** `recipes/services/ingredient_admin.py` holds pure query and
mutation functions with no HTTP concerns, so the HTMX views stay thin and the
behaviour is testable without a client. Views own request parsing, guards and
partial selection; services own the ORM.

**Typed names resolve case-insensitively.** `recipes/services/name_resolution.py`
is the only place the recipe editor turns a typed ingredient, tag or cuisine name
into a row: `resolve_ingredient` / `resolve_tag` strip the name, match it ignoring
case (keeping the stored spelling) and create it as typed only on a miss;
`find_ingredient` / `find_tag` / `find_cuisine` look up without creating, and
nothing creates a cuisine (see **Shared vocabularies**). The names carry a
`Lower(...)` unique constraint, so a raw `get_or_create(name=...)` would 500 on
`Onion` when `onion` exists (#34). Ingredient lookups take `owner` (the recipe's
owner) and see only the global list plus that owner's private rows, a global row
winning over a private one of the same name; a miss creates a row **private** to
the owner (plan 011). `ingredient_names_for(owner)` feeds the editor's datalist
from the same two sources, so no user ever sees another's private names. Plan
008's aliases extend `resolve_ingredient`.

**Selection lives in the request.** Checkboxes post `ingredient_ids`; every
re-rendered partial echoes them back. There is no client-side store: a change or a
search refreshes its own column and swaps the other affected fragments out of
band, so header counts, the tri-state select-all box and the enabled/disabled
state of Edit/Delete/Merge are all server-rendered. The column-2 header carries
the subsystem's only JavaScript, four lines of it, because `indeterminate` is a
DOM property with no HTML attribute and the dashed state cannot be rendered any
other way. The handler binds to the header wrapper rather than the checkbox:
htmx fires `htmx:load` on the root of swapped content and events bubble up, so a
listener on the nested input never sees it. The workspace carries the selection as
hidden inputs, since it replaces the column holding the checkboxes. `hx-include`
must name the inputs themselves (`.ingredient-pick:checked`, `.workspace-pick`) —
pointing it at a container element sends nothing.

**Repointing rule (important).** `IngredientInRecipe.ingredient` *and* `.substitute`
are both `on_delete=PROTECT`. No ingredient can be deleted while either FK
references it, so `delete_ingredients` and `merge_ingredients` repoint **both** onto
the replacement or survivor inside one transaction before deleting. Repointing an FK
leaves `index_in_sequence` alone, so recipe ordering is unaffected and
`utils/sequencing.py` is not involved. A delete with no usable replacement answers
422 and writes nothing rather than letting PROTECT surface as a 500. A recipe that
already held the survivor and a victim keeps both rows; de-duplicating a group is
out of scope.

**Orphans.** `search_ingredients(query, unused_only=True)` lists ingredients no
`IngredientInRecipe` references as either ingredient or substitute — the rows that
can be deleted outright, since neither FK PROTECTs them. Nothing prunes them
automatically: renames (`get_or_create` keeps the old row), last-use deletions and
imports all leave orphans, and deciding they are junk is the owner's call.

**Saving an edit.** The Edit workspace holds one panel per selected ingredient,
each posting itself. Saving the only panel closes the workspace (via `HX-Retarget`
onto `#columns`, since the form targets itself) — re-rendering a lone panel looks
like nothing happened. Saving one of several marks it and leaves the rest open,
because closing would discard whatever is typed in them; the panels carry the
selection so the view can tell the two cases apart.

**Owner scoping.** Recipes are owner-scoped and column 3 stays that way, but
the tool works on every ingredient, global or private: the delete confirmation
counts affected recipes across all owners, since a delete reaches recipes the
current user cannot see. Column 2 and the merge chooser badge a private row with
its owner (`_owner_badge.html`). A private row may only replace ingredients in
its own owner's recipes: `delete_ingredients` (and so every merge) raises
`IngredientScopeError`, a 422 with nothing written, rather than repoint another
user's recipe onto a row that user cannot see.

**Promote** is the fifth column-1 action (plan 011). `promote_ingredients` makes
each selected private row global, or merges it into the global row that already
has its name, then merges every other user's private row of that name into the
result, so all their recipes share it. The confirmation lists what each row
will fold in; the promoted rows stay ticked. The **Private only** filter
narrows column 2 to promotion candidates.

**Staff only (#46).** Every route is wrapped in `htmx_staff_required`
(`recipes/views/_auth.py`): anonymous users go to the login page as before, a
signed-in user who is not `is_staff` gets 403. An htmx request gets a short
plain-text 403, which the htmx config never swaps, so the global banner reports
it; a full-page visit raises `PermissionDenied` and Django renders `403.html`.
The home page shows the "Manage ingredients" link to staff only.

**Canonical names.** British spelling wins, enforced by
`UniqueConstraint(Lower("ingredient_name"), name="ingredient_name_ci_unique")`
(migration 0013; since migration 0018 it covers global rows only, and
`ingredient_name_ci_unique_per_owner` does the same within each user's private
rows) and mirrored in `IngredientForm`, which points a clashing rename at
the merge action. Databases predating the constraint are cleaned up with the
`find_ingredient_duplicates` command, which lists case-only clashes; merge them
before migrating.

**Three variant classes.** Case (`Onion`/`onion`) is the constraint above.
**Plural** (`onion`/`onions`) is the third: since the plural is a display form,
an `onions` row is bad data, so `find_plural_duplicates` pairs each row with the
row spelling out its `plural`, `search_ingredients(plurals_only=True)` narrows
column 2 to those pairs (composing with the query and the unused filter), and
`find_ingredient_duplicates` reports both classes. Back-filling is a merge in
the tool, never a data migration: picking which row survives is the owner's
call.

**Merge plural** is the fourth column-1 action and the one that fixes such a
pair. `merge_plural_ingredients` repoints recipes exactly as `merge_ingredients`
does, then writes the deleted row's name **verbatim** onto the survivor's
`plural_name` — the point of the action, since a plain merge drops the spelling
and leaves the rule to guess (`chili`/`chilis` would come back as `chilies`).
Verbatim even when the rule agrees, so the plural column visibly shows where the
merged name went; any prior override is overwritten, the merge being the later
and more deliberate statement. `suggest_singular` preselects whichever half
pluralises into the other, falling back to the first. Capped at **exactly two**
selected: with two plural rows there is no way to tell which spelling wins.
`_SELECTION_BOUNDS` carries each action's `(minimum, maximum)`; every other
action is still minimum-only. **Alias** — variants differing by more than case (`eggplant` →
`aubergine`) — is future work resolving on *input*: an `IngredientAlias` lookup
table applied at write time, so storage and display stay canonical. See
`docs/plans/008-ingredient-aliases.md`.

**Column-2 filters.** The views carry them as one typed mapping (`_Filters`:
`query`, `unused_only`, `plurals_only`, `private_only`), forwarded as `**filters` into the
context helpers, so adding a filter does not widen every call site.

Deleting the last `IngredientInRecipe` in a group, or moving every row out of it
via reassign, deletes the now-empty `IngredientGroup` too (`_prune_empty_group`),
compacting the remaining group indexes. A recipe's **last** group is always kept,
empty or not: the "+ Add ingredient" button is rendered inside a group block, so a
recipe with zero groups could only be refilled by adding a group first. The delete
response carries an `hx-swap-oob="delete"` for the vanished block plus a refreshed
reassign `<select>`, since the row swap alone would leave both stale.

### Step Titles (`Step.step_title`, `recipes/utils/step_title.py`)

Scraped recipes bury the heading of a step in the step itself — `<u>RAGÚ</u>:
Sauté the beef`, or `FOR THE STOCK: soak the kombu`. That heading is structure,
so it lives in its own optional field and the templates render it underlined
with a colon after it — the shape the scraped text wrote by hand — while the
colon itself stays outside `.step-title`, being punctuation rather than heading.
A step without a title renders exactly as it did before. Titles carry **no markup**: the `<u>` was
a wrapper around the heading, never part of it, so `_step_display.html` escapes
the title outright while `step_text` still goes through `safe_step_html`.

`recipes/utils/step_title.py` holds the recognition rule as a pure function,
free of Django imports. It is deliberately narrow — an inline-tag wrapper
(`<u>`, `<b>`, `<i>`, `<s>`) or an entirely upper-case run, closed by a colon,
followed by whitespace and something left over — so `Add salt: to taste` stays
whole. `sentence_case_heading` sits next to it and un-shouts a heading that is entirely
upper case (`FOR THE STOCK` → `For the stock`), leaving anything cased by hand
alone; proper nouns are lost with the shouting, since nothing in the text says
which words they were. Nothing calls either at import time: splitting and
un-shouting are a one-off backfill (`scripts/backfill_step_titles.py`), because
deciding that a colon introduces a heading is a judgement about legacy data, not
an import rule.

### Merging, Splitting and Bulk-Deleting Steps (`recipes/utils/step_text.py`)

Every displayed step carries a checkbox (`.step-select`, posting `step_ids`).
Checking one reveals the steps panel above the list — count, Merge, Delete,
Cancel — the same hidden-until-checked pattern as the ingredient reassign
panel; Merge stays disabled below two. The panel, any error and the `<ol>` live
in `_steps_block.html` (`#steps-block`), which every multi-row step action
re-renders whole; move up/down still swap only `#steps-list`.

- **Bulk delete** removes the checked steps through
  `remove_many_and_compact`, closing every gap at once.
- **Merge** appends the checked steps, however far apart, onto the one
  **highest up the page**, one space apart (`join_step_texts`). That step
  wins: it keeps its title and other fields; the others' titles go. The
  result is validated through `StepForm`, so an over-long merge answers 422
  and writes nothing rather than truncating.
- **Split at cursor** is a button in the edit form of a saved step. It posts
  the form as typed plus `split_at`, the cursor offset in code points (computed
  in `hx-on::config-request`; the server folds CRLF to LF so offsets match the
  textarea). `split_step_text` moves a cursor inside a word back to that word's
  start and refuses — 422, the form re-rendered with a message — when either
  half would be blank, i.e. the cursor is not after the first word and before
  the last. The head keeps the title; the tail becomes an untitled step right
  below. The form targets its own row, so success answers with `HX-Retarget`
  onto `#steps-block`. Inline tags cut by a split are left to the render-time
  sanitizer, which balances them.

Selections are posted with the request, never stored; a stale or foreign id is
ignored, so a merge or delete that matches nothing answers 422.

### Sequencing (`recipes/utils/sequencing.py`)

All `index_in_sequence` mutations go through shared, transactional helpers:
`insert_at_index` (create at a DOM position), `remove_and_compact`
(delete + close the gap), `remove_many_and_compact` (delete several + close
every gap, keeping the sequence's base), `move_in_sequence` (swap with a neighbour via a
`-1` sentinel for SQLite's per-statement unique checks). Entity views must
not reimplement index arithmetic.

Empty text fields (`short_description`, `group_name`, `unit`,
`preparation`) are stored as `""`, never `NULL`.

### Template Filters (`recipes/templatetags/recipe_filters.py`)

- `safe_step_html` — sanitizes step text, allowing only `<b>`, `<i>`, `<s>`, `<u>` inline tags; escapes everything else. Applied in `_step_display.html`.
- `safe_title_html` — the same for `Recipe.recipe_name`, allowing only `<s>` and `<u>`. Applied wherever the title is rendered as markup (`_field_display.html`, the recipe list, the delete panel, the metadata page, the clean-up tool's columns 3 and 4). Plain-text contexts — the `<title>` element and the `hx-confirm` prompt — use Django's `striptags` instead.
- `safe_blurb_html` — the same for `Recipe.short_description`, allowing `<b>`, `<i>`, `<s>`, `<u>` and turning new lines (and `<br>`) into `<br>`. Applied in `_field_display.html`.

  All three share `_InlineHtmlSanitizer`: tags lose their attributes and come out **balanced** — an unclosed tag is closed at the end and a stray closing tag is dropped — since the fragment lands inside a larger page and an unclosed `<u>` would underline everything after it. The markup is stored as typed; sanitizing happens on render only.
- `format_quantity` — strips trailing decimal zeros from `DecimalField` values (e.g. `2.50 → 2.5`, `4.00 → 4`), always in fixed-point notation. Applied in `_ingredient_display.html` and `_scaled_ingredients.html`.
- `display_ingredient_name` — the ingredient's name, pluralised when the quantity
  calls for it. Takes the whole `IngredientInRecipe`, since the decision needs
  name, quantity and unit together. Applied in `_ingredient_display.html` and
  `ingredient_admin/_recipe_preview.html`. See **Pluralisation** below.
- `scaled_quantity` / `ingredient_name_at` — the display-time scaling pair used by
  `_scaled_ingredients.html`: the quantity scaled by the page's `Fraction` and
  rounded for display, and the name pluralised for that displayed quantity. See
  **Scaling** above.

### Pluralisation (`recipes/utils/pluralise.py`, `Ingredient.plural`)

A plural is the display form of **one** ingredient at a quantity other than 1,
never a second row: `1 onion` and `2 onions` are the same `Ingredient`. It is
therefore presentation, computed on render, and nothing persists it — the
database always holds the canonical singular.

`recipes/utils/pluralise.py` holds the rule as a pure function with no Django
imports, so it is testable on its own. It inflects the **last word only**
(`spring onion` → `spring onions`) and leaves names already ending in `-s`
alone, since food nouns ending in `-s` are nearly always already plural or mass
(`oats`, `chives`, `asparagus`). `Ingredient.plural` layers the `plural_name`
override on top: blank derives from the rule, a value wins verbatim, and a value
equal to the singular makes the noun invariant (`broccoli`, `fish`). The
override is what covers the irregulars the rule deliberately does not chase, and
it is editable in the clean-up tool's Edit panel.

Two conditions gate the swap, both in `display_ingredient_name`: the quantity is
recorded and is not 1, **and** `unit` is empty. The unit check is what keeps mass
nouns safe — `200 g onion` must never become `200 g onions`. A page scaled with
`?servings=N` decides on the displayed quantity instead (`ingredient_name_at`), so
doubling 1 onion reads "2 onions".

### Shared vocabularies (multi-user)

Nutrisho is multi-user (#46). Recipes belong to their owner; the vocabularies
they draw on are split by who may change them:

- **Ingredients**: a global, staff-curated list plus a private list per user
  (plan 011). Only staff rename, merge or delete global ingredients, which is
  why the clean-up tool is staff-only. Typing an unknown name in the recipe
  editor creates a row private to the recipe's owner (`Ingredient.owner`);
  staff promote it to global in the clean-up tool.
- **Tags**: global tags curated by staff (in Django admin, owner blank) plus
  private tags per user (`Tag.owner`). The metadata form takes tags as
  comma-separated names; `resolve_tag` finds a global tag, then the owner's
  own, and creates a private one on a miss. Unique ignoring case within the
  global list and within each owner's tags; migration 0019 merged existing
  case-only duplicates into the most-used spelling.
- **Cuisines**: one global, curated tree, `area.region.subregion`
  (`med.italy.sicily`), via `Cuisine.parent` (PROTECT). A recipe points at any
  depth: `middle east` for a dish many countries claim, `med.italy` with no
  region. Areas are not all places: `anglo` is the US, UK, Ireland, Canada,
  Australia and New Zealand. Migration 0021 seeds the list agreed with the
  owner and folds the old flat names in (adjectives such as `Italian` via its
  `ALIASES`, else a node name occurring once; `fusion` and `modern` became
  global **tags**, being styles, not places; anything unmatched stays as a
  top-level row for staff). Users pick from the tree: the editor's datalist
  holds every dotted path (`cuisine_paths()`), `find_cuisine` takes a path or
  an unambiguous bare name, and an unknown name is a form error. Staff edit
  the tree in Django admin; `Cuisine.clean()` forbids dots in names, loops and
  a fourth level. Names are unique ignoring case among siblings
  (`cuisine_ci_unique_per_parent`) and among areas (`cuisine_ci_unique`).
- **Sources**: global, unchanged for now.

Every route that changes a global row checks `is_staff`, and its tests use the
`other_user` fixture to show a signed-in non-staff user is refused and nothing
is written.

### Key Models

- `Recipe` — core entity, owns name, description, cuisine, source, owner, servings (author's intended serving count; mandatory, NOT NULL, defaults to 1, constrained to `>= 1`)
- `Ingredient`, `IngredientGroup`, `IngredientInRecipe` — ingredient hierarchy; `IngredientInRecipe.quantity` is stored as-is from source data (not normalized to per-serving). `Ingredient.owner` is NULL for the global list or the user a row is private to, and `ingredient_name` is unique case-insensitively among global rows and within each owner's private rows; `Ingredient.plural_name` is an optional display-only override for the pluralisation rule (blank derives it); `IngredientInRecipe.ingredient` and `.substitute` are both `PROTECT`
- `Step` — ordered recipe steps; `step_title` is an optional heading, stored as `""` when absent and rendered underlined in front of the step text, followed by a colon
- `Cuisine`, `Source`, `Tag` — lookup/classification models; `Cuisine` is a node of the cuisine tree (`parent`, at most three levels), its name unique case-insensitively among its siblings; `Tag.owner` is NULL for a global tag or the user it is private to

### Data Flow

Browser → HTMX views → Django ORM → SQLite. The database is the only copy of the
data; the YAML seed files and their import/export commands were bootstrap
scaffolding and are gone (issue #27).

`backup_db` (`make backup`) writes `docs/schema.sql` (committed, schema
only, deterministic order) and `docs/dump-<timestamp>.sql` (git-ignored, full
dump for restoring with `sqlite3`). SQLite only, like the rest of the app. The
dump is read inside one read transaction, so it is a consistent snapshot even
while the app writes (WAL lets those writes carry on).

`delete_recipe --id <N>` removes recipes by primary key.

### Concurrent writes

`settings/base.py` gives SQLite `transaction_mode: IMMEDIATE`, a 20 s busy
timeout, `journal_mode=WAL` and `synchronous=NORMAL` (issue #38). Write paths
read and then write inside `atomic()`, and `select_for_update()` is a no-op on
SQLite, so it is the IMMEDIATE write lock taken at `BEGIN` that serializes
them; with Django's default DEFERRED mode, overlapping writes fail with
`database is locked` instead of waiting. The database is three files
(`db.sqlite3`, `-wal`, `-shm`) that must be copied, moved and deleted together;
see the developer guide for the backup rules and the one-off switch of an
existing database. Tests use the same options on a temporary file database.

### Logging and health check

`settings/base.py` sends every log record to stderr through one handler on the
root logger (issue #43). The `django`, `recipes` and `nutrisho` loggers carry no
handlers of their own, only a level from `LOG_LEVEL` (default `INFO`), and
propagate to root; `django.security` is pinned at `WARNING`. Keep it that way:
a logger with `propagate: False` or its own handler would bypass the console
and pytest's `caplog`. Failed logins are logged by a `user_login_failed`
receiver in `recipes/signals.py`, connected in `RecipesConfig.ready()`.
Sentry is optional and initialised in `settings/prod.py` only when
`SENTRY_DSN` is set.

`GET /healthz` (`nutrisho/health.py`) is the one public route: it is marked
`login_not_required` so it stays open once login is enforced site-wide, never
cached, and answers 200 or 503 depending on `SELECT 1`.

### How far SQLite goes

Orders of magnitude for a small NVMe VPS, not benchmarks:

- Reads never block each other or the writer; tens of thousands of simple
  queries a second.
- Writes queue one at a time. A click here is a short transaction of about
  1 ms, so several hundred writes a second before anyone waits; 10 active users
  make about 2.
- A recipe is a few KB; 100,000 recipes is a few hundred MB.

Signals to move to Postgres, usually one of these rather than a user count:

1. A second app server, or the database on its own host. SQLite must sit on
   the app machine's local disk, never a network volume.
2. Writes queue: `database is locked` errors or rising p95 latency on saves
   despite IMMEDIATE and the 20 s timeout. Start planning at a sustained ~50
   writes a second.
3. Long write transactions (bulk imports, large merges) block every other
   writer for their whole duration.
4. Features or operations SQLite lacks: `pg_trgm` fuzzy search, read replicas,
   migrations without a table rebuild.

Until then, keep gunicorn to 2-4 workers. The move itself is mostly a data
copy: the code already uses `select_for_update` and portable constraints, but
Postgres enforces the `max_length` caps SQLite ignores.


## Constraints

- Prototype quality: no production settings, no secrets management
- SQLite only; no migrations for external DBs
- No REST API yet
- Auth uses Django's built-in User model; the owner superuser comes from
  `bootstrap_owner` (`make bootstrap`), never from credentials in the repo

## Boundaries

- `src/nutrisho/` — project config only, no business logic
- `src/recipes/` — all domain logic
- `src/recipes/services/` — pure query/mutation functions; no HTTP, no templates
- Management commands in `src/recipes/management/`
